# Deployment

Frontend on Vercel, API on Render, database on MongoDB Atlas. All three have a
free tier that runs this without a card.

```
browser ──▶ Vercel (static)  ──▶ Render (Express)  ──▶ Atlas (MongoDB)
                                       │
                                       └──▶ Gemini / Groq
```

The API key never reaches the browser. Everything AI-shaped goes through our own
server, which is also what makes rate limiting possible at all.

---

## 1. MongoDB Atlas

1. **cloud.mongodb.com** → sign up → **Build a Database** → **M0**, the free tier.
2. Region: **Mumbai (ap-south-1)** if offered — closest to both the users and the
   Render region below.
3. **Database Access** → add a user with a password. Write it down; it goes into
   the connection string.
4. **Network Access** → **Allow access from anywhere** (`0.0.0.0/0`).

   This looks careless and is not: Render's free tier gives no fixed outbound
   address, so there is nothing narrower to allow. The database stays protected
   by credentials rather than by network position. On a paid plan with a static
   IP, restrict it.
5. **Connect** → **Drivers** → copy the connection string and put the database
   name in it:

   ```
   mongodb+srv://USER:PASSWORD@cluster0.xxxxx.mongodb.net/lakshya?retryWrites=true&w=majority
   ```

   If the password has `@`, `/`, `:` or `#` in it, URL-encode those characters or
   the string will not parse.

## 2. Render — the API

The repository has a `render.yaml`, so this is a blueprint deploy rather than a
form to fill in.

1. **Render → New → Blueprint** → connect this repository.
2. Render reads `render.yaml` and asks for the values marked `sync: false`:

   | Variable | Value |
   |---|---|
   | `MONGODB_URI` | The Atlas string from step 1 |
   | `GEMINI_API_KEY` | From [Google AI Studio](https://aistudio.google.com/apikey) |
   | `GROQ_API_KEY` | From [Groq Console](https://console.groq.com/keys) |
   | `CLIENT_ORIGIN` | The Vercel URL — fill in after step 3, see below |

   `JWT_SECRET` is generated by Render itself, so it is not something anyone has
   typed or reused.

3. Deploy. It is up when `https://<service>.onrender.com/api/health` answers:

   ```json
   { "data": { "status": "ok", "database": "connected", "ai": { "available": true } } }
   ```

   `status: degraded` with a 503 means the database is unreachable — almost
   always the Atlas IP allowlist or a mis-encoded password.

## 3. Vercel — the frontend

1. **Vercel → Add New → Project** → import this repository.
2. **Root Directory: `frontend`.** This is the only setting that matters;
   `frontend/vercel.json` supplies the rest.
3. Environment variable:

   | Variable | Value |
   |---|---|
   | `VITE_API_URL` | `https://<your-render-service>.onrender.com/api` |

   Note the `/api` on the end. It is baked in at build time, so changing it later
   needs a redeploy, not just a restart.

4. Deploy, then **go back to Render and set `CLIENT_ORIGIN`** to the Vercel URL —
   scheme, host, no trailing slash:

   ```
   CLIENT_ORIGIN=https://lakshya-xyz.vercel.app
   ```

   Get this wrong and every request fails in the browser with a CORS error while
   working perfectly from curl. It is the single most common way this deployment
   breaks.

## What is already handled in the code

| Concern | How |
|---|---|
| SPA deep links | `vercel.json` rewrites everything to `index.html`, so refreshing `/goals/abc/plan` loads the app instead of a 404 |
| Response size | gzip on every response — a study plan goes from 6 KB to 0.8 KB |
| Proxy headers | `trust proxy` set to one hop, so rate limits see the real client rather than the load balancer, and a forged header cannot dodge them |
| Unhealthy instances | `/api/health` answers 503 when the database is down, so Render pulls the instance out of rotation |
| Restarts and deploys | SIGTERM stops new connections, lets in-flight requests finish, closes the database, and force-exits after 15s so a hung request cannot block a deploy |
| Connection limits | Mongoose pool capped at 10 — Atlas M0 allows a few hundred across the cluster and the default would let two instances exhaust it |
| Crashes | An uncaught exception shuts down cleanly and lets the platform start a fresh process, rather than serving from a process in an unknown state |
| Long AI calls | Socket and header timeouts sit above the 45s provider timeout, and keep-alive sits below the header timeout so a proxy cannot reuse a socket we are closing |
| Caching | Hashed assets are immutable for a year; the 3D models for a week |
| Secrets | Nothing in the repository. `.env` is ignored, Render holds the values encrypted, and `JWT_SECRET` is machine-generated |

## Rate limiting

Two limits, keyed per account once a request is authenticated and by IP before
that. Keying on IP alone would be wrong here — a whole college sits behind one
address, and one impatient student would lock out a classroom.

| Limit | Window | Applies to |
|---|---|---|
| 300 requests | 15 min | everything |
| 20 requests | 1 hour | anything that spends an AI generation |
| 20 attempts | 15 min | sign in and sign up, keyed by IP |

The AI limit is the one that matters. Generating a topic graph, quiz, notes or a
tutor reply draws on a **shared daily allowance** — roughly twenty per model per
day for the whole deployment, not per user. Without that limit one person holding
down a button empties it for everybody else for the rest of the day.

## What the free tier will actually do to you

Worth knowing before a demo rather than during one.

**Render sleeps after 15 minutes of inactivity.** The first request after that
takes **around 50 seconds** while the instance cold-starts, and it looks exactly
like the app being broken. Open the deployed site a minute before demonstrating
it. A paid instance removes this entirely; nothing in the code can.

**The AI allowance is shared and small.** About twenty generations per model per
day across everyone using the deployment. Generate a plan or two before a demo so
the material is already there — everything cached, including topic notes, is
served from the database and costs nothing.

**Atlas M0 is shared hardware.** Fine for this, slower under load than the numbers
above suggest.

None of these are architectural. The same code on paid tiers has no cold start, a
real quota and dedicated database hardware, and nothing about the deployment
changes except the plan.

## Verifying a deployment

```bash
# up, and the database is reachable
curl https://<service>.onrender.com/api/health

# an account can be made end to end
curl -X POST https://<service>.onrender.com/api/auth/register \
  -H 'content-type: application/json' \
  -d '{"name":"Check","email":"check@example.com","password":"studypass1"}'
```

Then in the browser, on the Vercel URL: sign up, open the network tab, and
confirm the requests go to the Render host and come back `200`. Navigate to a
plan and **refresh the page** — that is the check that the SPA rewrite is working.

### One trap when building locally

If `NODE_ENV=development` is set in your shell, `npm run build` produces the
**development** build of React — 132 kB gzipped instead of 78 kB, with the slower
dev-mode checks compiled in. It succeeds silently, so the only sign is the bundle
size in the build output.

Vercel sets `NODE_ENV=production` itself, so a deployed build is never affected.
It only bites when testing a production build by hand. If the main chunk is much
over 80 kB gzipped, that is the reason.
